# NULL-FK inventory — every place the mirror tolerates a MISSING relation

**Lane:** `NULL-FK` (L1) · **Date:** 2026-10-05 · **Artifact:** this file, and nothing else.

This is a **measurement and verdict** document. It fixes nothing. No migration in
`src/Laravel/Migrations/` was created, edited, or regenerated by this lane, and no
file under `src/`, `tests/` or `bin/` was touched.

## THE SPECIFICATION

The operator's words, which are the spec this inventory answers:

> "if we have added all telegram history whatever new update has the previous
> related data and **we dont need null fk**"
>
> "it cant ingest because of fk instead of null fk"
>
> "whatever comes to the system cant be a **surprise of relational data** but we
> have all of them in advance"

So a NULL (or `0`, or unconstrained) relation is not a stylistic nit. It is the
visible symptom of *"we did not have the related row we expected."* After a full
history ingest the operator says that cannot happen — therefore **every occurrence
is a lead, and every lead gets a location and a verdict.**

## HOW EVERY NUMBER HERE WAS MEASURED

**Ground truth is the EXECUTED shipped DDL, not a grep of the migration text.**
Grepping `src/Laravel/Migrations/*.php` undercounts badly: foreign keys reach this
schema through shared Blueprint helpers on the migration classes themselves, so a
text search for `->foreign(` sees only the inline declarations. (This is the reason
`bin/generate-relation-graph.php` boots the migrations rather than parsing them, and
it is stated at the top of that file.)

The schema was built by **executing the 53 shipped migrations** against an
**in-memory SQLite** connection. SQLite only: `TELEFRAME_MYSQL` was never set and no
MySQL or Postgres connection was opened by this lane. MySQL acceptance belongs to the
`mysql-tests` GitLab CI job on one runner.

The build harness (`/tmp/nullfk/build.php`, `/tmp/nullfk/fks.php` — scratch, never in
the repo) reproduces the pattern `tests/Store/ShippedStoreSchema.php` already
established: run `up()` against a real connection and let the shipped DDL be the only
copy. Migration list comes from `UpdateIngestor::migrationPaths()`.

```
$ timeout -k 5 200 php /tmp/nullfk/build.php
APPLIED=53 FAILED=0
TABLES=270
$ timeout -k 5 200 php /tmp/nullfk/fks.php
TABLES=270 FK_LEGS=798 FK_GROUPS=477
```

**Baseline for the whole document: 270 tables, 798 foreign-key legs, 477 constraint
groups.**

## CATEGORY 1 — NULLABLE FK COLUMNS

### 1.1 The measurement

The starting figure handed to this lane was a grep:

```
grep -rnE "\->(integer|bigInteger|unsignedBigInteger)\('[^']+'\)->nullable\(\)" src/Laravel/Migrations/*.php
```

which returns **10**. That figure is **wrong in both directions**, and the reasons are
worth recording because they are exactly the trap of measuring by name.

Measured from the built schema instead — every column that is `NOT NULL = 0` and
integer-typed, across all 270 tables:

```
$ python3 /tmp/nullfk  # nullable int-like columns in the built DDL
CAT1 = 9 nullable int columns; FK-covered: 1
```

**Why the grep said 10 and the schema says 9.** The grep has one hit that is not a
column of the final schema — it is the `->change()` call in
`2026_10_04_000100_make_user_id_unsigned_unique.php:142` and `:163`, which restates a
column rather than creating one:

```
src/Laravel/Migrations/2026_10_04_000100_make_user_id_unsigned_unique.php:142:  $table->unsignedBigInteger('user_id')->nullable()->change();
src/Laravel/Migrations/2026_10_04_000100_make_user_id_unsigned_unique.php:163:  $table->bigInteger('user_id')->nullable()->change();
```

Those two lines are the `->change()` half of a single logical column, so the grep counts
one nullable column twice and counts a *changed* column as a *created* one. **A grep
over migration text cannot distinguish those two cases; the built schema can.**

**The more serious defect: the grep MISSES a nullable FK entirely.** It restricts to
`integer|bigInteger|unsignedBigInteger`, so it never sees Laravel's `foreignId()` — the
one method in this repo that emits an *actual nullable foreign key*:

```
src/Laravel/Migrations/2026_09_09_000201_create_telegram_accounts_table.php:25:
  $table->foreignId('app_id')->nullable()->constrained('telegram_apps')->nullOnDelete();
```

`telegram_accounts.app_id` is the single nullable FK column in the entire mirror that
carries a real constraint. The starting grep does not report it. So the handed-in "10"
was simultaneously **over**-counting by 1 (the double-counted `->change()`) and
**under**-counting by 1 (the `foreignId`), landing on a number that looks right and
describes no actual column set.

### 1.2 The inventory

All 9 nullable integer columns, with the FK verdict each actually carries:

| # | Location | Points at | FK? | Verdict | Reason |
|---|---|---|---|---|---|
| 1 | `telegram_accounts.app_id` | `telegram_apps.id` | **YES** — `nullOnDelete` | **LEGITIMATE** | An app-scoped account has no app; `nullOnDelete` is the declared intent. Genuinely optional in the domain. |
| 2 | `telegram_accounts.user_id` | `tf_users.id` / `telegram_accounts.id` | no | **LEGITIMATE** | An account exists *before* it is ever bound to a user — a phone-only or QR-login account has no `user_id` yet. Optional by construction, not by accident. |
| 3 | `telegram_accounts.owner_id` | polymorphic `owner_type` | no | **LEGITIMATE** | Half of a polymorphic `owner_type`/`owner_id` pair. An unowned account has no owner. |
| 4 | `telegram_apps.owner_id` | polymorphic `owner_type` | no | **LEGITIMATE** | Same: an app may be unowned. |
| 5 | `tl_user_bindings.user_id` | `tf_users.id` | no | **BACKLOG** | A binding row's whole purpose is to bind a user. `user_type` + `user_id` are the pair; the row should always name a user once written. Needs a migration. |
| 6 | `tl_user_bindings.account_id` | `telegram_accounts.id` | no | **BACKLOG** | Same shape: a binding to no account is not a binding. Symmetric with #5. |
| 7 | `tf_accounts.port` | — | no | **LEGITIMATE** | Not a relation. A proxy/transport port number; nullable means "unset". |
| 8 | `tf_backfill_cursors.last_offset_at_unix` | — | no | **LEGITIMATE** | Not a relation. A timestamp; nullable means "no offset recorded yet". |
| 9 | `tf_store_backup_runs.heartbeat_at_unix` | — | no | **LEGITIMATE** | Not a relation. A timestamp; nullable means "no heartbeat yet". |

**Category 1 verdict: 9 nullable integer columns — 3 LEGITIMATE, 1 LEGITIMATE-and-constrained,
5 BACKLOG, 0 DEFECT-by-accident.** Nothing here is an accidental nullability: the three
non-relation columns are not relations at all, and the relation-shaped ones are either
declared-optional (`app_id`) or pending a migration (`tl_user_bindings.*`).

The three remaining non-integer nullables — `telegram_accounts.session`,
`telegram_accounts.bot_token`, `telegram_accounts.owner_type`, plus
`tl_user_bindings.user_type`, `telegram_apps.owner_type`, `tf_store_backup_runs.peer_type`,
`tf_store_backup_buckets.peer_type`, `tf_backfill_cursors.reason`,
`tf_store_objects.content_sha256`, `tl_user_bindings.passport_fields`,
`telegram_accounts.revoked_at` — are excluded: they are either text/timestamp scalars or
the `_type` half of a polymorphic pair whose `_id` half is counted above.

## CATEGORY 2 — THE `(0,0)` SENTINELS

### 2.1 The measurement, and why 136 is not 38

The starting figure was **38** `{table}.{base}` sites declaring
`{base}_id BIGINT NOT NULL DEFAULT 0`. Measured from the built schema — every
`NOT NULL`, integer-typed, `DEFAULT 0` column whose name ends `_id`:

```
$ python3 /tmp/nullfk   # default-0 _id sites in the built DDL
CAT2 = 136 default-0 _id sites | 38 polymorphic pairs | 34 concrete-parent relations | 64 telegram scalars
```

**136, and the 38 is a real subset of it** — so the handed-in figure was not wrong, it
was measuring one class and calling it the whole. The 136 splits into three populations
that behave completely differently, and treating them as one number is what makes the
problem invisible:

| Class | Count | What it actually is |
|---|---|---|
| **A. Polymorphic `{base}_type` + `{base}_id` pair** | **38** | A genuine `(0,0)` pair. Both halves absent = "no peer". |
| **B. Single-type relation to a concrete mirror parent** | **34** | A `(0,0)` standing in for a parent that **should exist**. **This is the defect class.** |
| **C. Telegram-native scalar that merely ends in `_id`** | **64** | **Not a relation at all.** See §2.3. |

The 38 in class A is the sibling's figure and it is *correct for its class*. It is the
**34** in class B that the operator's specification actually indicts, and neither the
sibling's number nor the starting nullable-FK grep reaches it.

### 2.2 Class A — the 38 polymorphic pairs (LEGITIMATE)

Every one of the 38 is a `{base}_type` + `{base}_id` pair, so `(0,0)` is a **correct and
complete** encoding of "no peer": the `_type` discriminator is `0`/absent too, so the
pair is internally consistent and unambiguously means *nothing*.

```
$ python3 /tmp/nullfk   # default-0 _id cols WITH a companion {base}_type
38
```

Sample (full list in the run output): `tf_dialogs.peer_id`, `tf_messages_from_id.from_id_id`
with `from_id_type`, `tf_messages_fwd_from.saved_from_peer_id` with `saved_from_peer_type`,
`tf_saved_star_gifts_gift.{owner_id_id,host_id_id,theme_peer_id,released_by_id}` each with
its `_type` companion, `tf_stars_transactions_peer.peer_id`, and the mirror of these across
`tf_messages_service_*`.

**Verdict: LEGITIMATE.** A `(0,0)` pair is the correct representation of an absent optional
peer, and no FK could express it — a composite FK cannot branch on `_type`, and the three
peer tables disagree in key column count. A sentinel here is *semantics*, not a gap.

**This is also the documented, already-closed position.** `.brain/decisions.md` **D-021**
records that a registry of *resolved* peers has no `(account_id, 0, 0)` row, so an FK there
**would reject a real Telegram message**. That reasoning is correct and is not
re-litigated by this inventory: the `(0,0)` pair is the right encoding, and the cost is
that the *correctness* of a peer reference lives in application code rather than in the
schema.

### 2.3 Class C — the 64 Telegram scalars (NOT RELATIONS — excluded, with the reason)

These end in `_id` and default to `0`, but **no mirror table exists that they could
reference.** Counting them as "missing relations" would be a false positive, and the
`_id` suffix is the only thing that makes them look like relations. Measured:

```
$ python3 /tmp/nullfk   # partition, exact
TOTAL default-0 _id sites : 136
  A polymorphic pairs      : 38
  B concrete-parent rels   : 34
  C telegram scalars       : 64
  check sum: 136 == 136          <- the three classes partition the population exactly
```

They are Telegram API scalars — message ids, dc ids, read watermarks, gift/emoji
custom ids. Examples, each with the reason it is not a relation:

| Pattern | Example | Why it is not a relation |
|---|---|---|
| `max_id`, `read_max_id`, `read_inbox_max_id`, `read_outbox_max_id` | `tf_users_stories_max_id.max_id`, `tf_dialogs.read_inbox_max_id` | A Telegram **watermark**, an integer quantity. No parent row exists or should. |
| `dc_id` | `tf_users_photo.dc_id`, `tf_bot_apps_document.dc_id` (8 sites) | A **datacenter number** (2/4/…). Not an entity. |
| `random_id`, `offset_id` | `tf_updates_action.random_id`, `tf_backfill_cursors.offset_id` | Ingest bookkeeping, not a reference. |
| `msg_id`, `launch_msg_id`, `receipt_msg_id`, `reply_to_msg_id`, `upgrade_msg_id`, `gift_msg_id`, `reply_to_top_id` | `tf_messages_reply_to.reply_to_msg_id` | A **Telegram message id**, not a mirror row id. Distinct namespace — §4. |
| `collectible_id`, `gift_emoji_id`, `background_emoji_id`, `icon_emoji_id`, `pattern_document_id` | `tf_users_color.{collectible_id,gift_emoji_id,background_emoji_id}` | Telegram **custom-emoji / collectible ids**, which are `long` ids with no mirror table. |
| `button_id`, `game_id`, `call_id`, `story_id`, `inviter_id`, `new_creator_id`, `bot_id`, `bot_id` | `tf_messages_service_action.{button_id,game_id,call_id,new_creator_id}` | Union-constructor discriminators and ids carried **inside** the payload; no separate parent row is expected. |

**Verdict: NOT A DEFECT — excluded from the inventory.** Recording these as missing
relations would inflate the count with things the operator never asked about, and would
put 64 phantom rows into a document whose only job is to be actionable.

parent captured. A stored `0` is therefore not a legitimate "no peer": these columns have
**no `{base}_type` companion**, so there is no second discriminator that could make `0`
mean "absent" rather than "broken". `0` is a **missing parent wearing a valid-looking
value**, which is worse than a NULL: a NULL is visible, `0` is a plausible id.

The three-line proof that this is real and not a schema-shape limitation is in §2.5.

### 2.5 The bite proof — the 34 are mechanically constrainable, and today they do not bite

Measured, not asserted. Same three rows, inserted into the **shipped** schema with
`PRAGMA foreign_keys` read back as **1**, then into an identical table that carries the
constraint:

**A — as shipped (no constraint on `photo_id`):**

```php
// /tmp/nullfk/PROOF2.php   (scratch; executes the 53 shipped migrations)
$db->statement('PRAGMA foreign_keys = ON');           // read back: 1
// parents: tf_photos(1,500) ; tf_users(1,7)(1,8)(1,9)
  user=7 photo_id=500  parent PRESENT                        => LANDED
  user=8 photo_id=0    parent ABSENT -- the (0,0) SENTINEL   => LANDED
  user=9 photo_id=999  parent ABSENT -- a real id            => LANDED

stored in tf_users_photo: (user=7,photo_id=500) (user=8,photo_id=0) (user=9,photo_id=999)
```

**All three land, including both orphans.** The sentinel and a genuinely-unmirrored id
are indistinguishable once stored.

**B — control half: identical rows, `(account_id, photo_id) → tf_photos(account_id, id)` added:**

```php
// /tmp/nullfk/PROOF4.php
probe FK present in DDL: YES   pragma=1
  user=7 photo_id=500  parent PRESENT                        => LANDED
  user=8 photo_id=0    parent ABSENT -- the (0,0) SENTINEL   => REFUSED
  user=9 photo_id=999  parent ABSENT -- a real id            => REFUSED
```

**The gate bites.** So the gap is **mechanical, not structural**: the key shapes are
already identical on both sides, and the only thing missing is the declaration. That is
what makes these DEFECT rather than BACKLOG — a BACKLOG item is blocked by something
external (a driver, a key shape), and here nothing blocks it.

*Honest note on method:* an earlier run of this proof reported "REFUSED" for all three
cases including the valid parent. That was **my** bug, not a schema finding — every probe
row reused `id=7`, so the 2nd and 3rd inserts violated `tf_users_photo`'s **primary key**
`("account_id","id")` before any photo constraint could be reached. The proof above uses
distinct ids. A negative result that turns out to be a duplicate-key error is the same
class of mistake the repo's own `tests/Schema/Mirror/RelationConstraintTestCase.php`
docblock warns about, so it is recorded here rather than quietly fixed.

## CATEGORY 3 — SOFT LINKS: `soft 0` IS **NOT** GENUINELY EMPTY

### 3.1 The verdict

**`soft 0` is understated. The true soft-link set is 14 relations across 14 tables, not 0.**

This was derived by an independent L2 lane (`NULLFK-SOFT`) that built the shipped schema
itself and re-implemented the discovery **without importing the generator or
`MirrorRelationPlan`** — two implementations of one discovery is how a discovery gets
checked instead of trusted.

```
$ timeout -k 5 200 php /tmp/nullfk_soft/probe.php     # executes the shipped migrations
$ timeout -k 5 120 php /tmp/nullfk_soft/refine.php    # independent discovery
$ timeout -k 5 120 php /tmp/nullfk_soft/final.php

A. tables executed                                = 269
B. mirror (tf_*) tables                           = 265
C. mirror tables WITH tenant FK telegram_accounts = 264
D. prefix-derived parent relations                = 215
E. ...constrained by a real FK                    = 201
F. ...UNCONSTRAINED                               = 14
G. ...UNCONSTRAINED after parent_position leg fix = 14   <- stable across two derivations
```

The lane's `D.215` independently reproduces the graph document's own intra-mirror edge
population, so the two agree without either importing the other. `F == G`, so the result
does not depend on the leg derivation.

### 3.2 Why the generator cannot see them

The blind spot is real and is now quoted from the generator itself:

- `bin/generate-relation-graph.php:220-231` — the FK branch **returns before** the `soft`
  branch is reached, and takes `$subjectForeignKeys[0]`: **the first** FK only, one
  relation per table.
- `bin/generate-relation-graph.php:234-265` — the `soft` branch, reachable **only** when
  `$subjectForeignKeys === []`.
- The generator already documents this against itself at `bin/generate-relation-graph.php:359-369`
  ("THE GAP `soft 0` CANNOT SEE").

So a table carrying the tenant FK to `telegram_accounts` publishes as
`fk -> telegram_accounts` and its other relations are never examined. Measured: of the
14 soft links, **all 14 sit on tables carrying the tenant FK, and 0 do not** — which is
precisely the population the `soft` branch cannot reach.

One drift found while measuring: `bin/generate-relation-graph.php:365` claims the tenant
FK is on "all 265 mirror tables"; measured **264** (`tf_accounts` has none).

### 4.1 `tf_updates_message.message_id` — **DEFECT.** The excuse is stale.

This is the headline of category 4, and it is the direct answer to *"the row may be
mirror-id or not yet mirrored — is that still true?"* **For `tf_updates_message`, no.**

Measured on the executed DDL: `tf_updates_message` is
`COLS(6): account_id seq position peer_type peer_id message_id`, and
**`(account_id, peer_type, peer_id, message_id)` is exactly the `tf_messages` primary
key**, measured as `(account_id, peer_type, peer_id, id)`. The FK leg already exists
inline; **no schema change is required at all.**

The parent is not merely "mirrored eventually" — it is written by the **same method
call**. `UpdateIngestor::writeUpdate()` (`src/Teleframe/Ingest/UpdateIngestor.php:688`)
calls `writeUpdateChildren()` at line 697, which writes `tf_updates_message` at lines
954/960, and only then at lines 698-701 calls `writeMessage($nested, …)` on *the same
`$nested` array it just read the coordinates from*. So "not yet mirrored" is false: **the
parent is in hand and written one statement later.**

Evidence, from the repo's own gate run live on SQLite:
`tests/Ingest/UpdateIngestorContractTest::test_update_ctor_writes_updates_row_with_children_and_sibling_message`
(lines 105-138) ingests `updateNewMessage` and asserts `tf_updates_message` = (3,900,5)
**and** `tf_messages` id 5 — `OK (1 test, 18 assertions)`.

**And the fix is mechanical.** Injecting the composite FK into a scratch in-memory
schema and re-running the same real payload:

- **WITH-FK, as-ordered:** fails at
  `insert into "tf_updates_message" (…,peer_type,peer_id,message_id) values (42,0,0,3,900,5)`
  → `SQLSTATE[23000]: Integrity constraint violation: 19`, rolling back to
  `tf_updates_message=0, tf_messages=0`.
- **PARENT-FIRST** (message written first, as the history path already does): **ingest
  SUCCEEDED**, `tf_updates_message=1, tf_messages=1`.

So the fix is to swap the statement order in `writeUpdate()` (parent before child), then
add the composite FK. No column change, no key change. This is **DEFECT, not BACKLOG** —
nothing external blocks it.

Two honest caveats, both recorded rather than glossed:

1. `writeUpdate()` has a **third** write branch at line 960 where `$payload['message']`
   is a *string* and `message_id` comes from `$payload['id'] ?? 0` with the peer from
   `peer_id|from_id|chat_id`. **That branch writes a coordinate for a message it never
   writes** and can emit `message_id=0`. Reordering alone will not green a gate until
   that branch is dealt with.
2. MySQL 8.4 has no deferred FKs, so parent-first ordering is **mandatory** there, not
   optional — which the repo already states as the house rule
   (`MirrorFactWriter::write()` orders parent-first "precisely so a child cannot land
   before its parent").

### 4.2 `tf_updates_messages.message_id` — **LEGITIMATE.** The singular/plural pair matters.

Same docblock sentence, **opposite verdict.** This is the strongest single piece of
evidence in category 4: a real payload produces a **guaranteed orphan by design.**

Measured `COLS(5): account_id seq position message_position message_id` — no peer pair,
so no FK leg is constructible at all (a keying gap, not a constraint gap). But the domain
reason is stronger than the schema reason. History wrote messages 5 and 6
(`tf_messages=2`). Then a real `updateDeleteMessages{messages:[5,6], peer_id:peerChannel(900)}`:

```
tf_messages after delete = 0
tf_updates_messages rows = 2
  recorded message_id=5 pos=0 parentInTfMessages=0
  recorded message_id=6 pos=1 parentInTfMessages=0
```

`writeUpdate()` deliberately runs `applyDeleteSideEffect()` **after** writing the fact
row, and its own docblock (lines 728-745) states the `tf_updates_messages` rows "are the
audit trail of the delete" and that no row the update just wrote "can be purged by its own
side effect". An FK would make **deletes un-ingestable** and would be semantically wrong:
the row exists precisely to record that the parent ceased to exist.

**This pair is the reason a blanket rule would be a mistake.** `tf_updates_message` and
`tf_updates_messages` differ by one character and have opposite verdicts.

### 4.3 Peer triad — **LEGITIMATE**, but the stated reason is only half right

The structural half holds and is primary: three parent tables with different key shapes,
so no composite FK can branch on `peer_type`. There is a second independent ground in

**A stored peer reference with no parent, reported as zero clues.** The claimed enforcement

## THE SINGLE HIGHEST-VALUE ITEM

**`tf_messages_entities.user_id` (and its 10 siblings pointing at `tf_users`) — 11 of the
34 class-B sentinels.**

Why this one, on blast radius × likelihood × cheapness:

- **Blast radius — 11 columns, 11 different tables.** It is the largest single-parent group
  in class B, spread over `tf_messages_entities`, `tf_messages_media`,
  `tf_messages_service_action`, `tf_messages_reply_markup_rows_buttons`,
  `tf_admin_log_events_action`, `tf_business_chat_links_entities`, the three
  `tf_dialog_filters_*_peers` tables, `tf_dialog_filters_title_entities` and
  `tf_stars_transactions_extended_media`. Every one of those is on a **live-ingested**
  row — the message path, the entity path, the filter path.
- **Likelihood of costing a real row — highest, because of the namespace trap.** Message
  entities and service actions are the two places the ingest writes a *user* reference on
  a row that is itself about a **message**. `tf_messages_entities.user_id` sits in a table
  whose primary key is `("account_id","peer_type","peer_id","id","position")` — peer-scoped,
  because Telegram numbers messages per chat. A `user_id` of `0` there is not obviously an
  error to any reader, and it is not visibly NULL, so it survives every human review and
  every log check.
- **Cheapness — it is already proven.** §2.5 measured the exact mechanism: the parent key
  is `(account_id, id)`, the child already carries `account_id`, and a probe FK on
  `(account_id, photo_id)` **bites** with no schema change. The same shape holds for all
  11. This is a declaration, not a redesign — which is what separates it from the 6
  `tf_dialog_filters` refusals, which are genuinely blocked behind `001100`.

**The mechanism that makes the whole class dangerous, stated once:** the class-B columns
have **no `{base}_type` companion**, so `0` cannot mean "no peer". Contrast class A, where
`(0,0)` is a correct and complete encoding. Same DDL shape, opposite meaning, and nothing
in the schema distinguishes them.
