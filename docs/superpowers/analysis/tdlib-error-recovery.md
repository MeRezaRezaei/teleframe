# TDLib Error Recovery & Connection Resilience Analysis

## Overview

This document maps every error path in TDLib (Layer 227-era source, September 2026 snapshot) to its
concrete response, then compares the patterns against Teleframe's current implementation. TDLib's
error handling lives across four layers, from lowest to highest:

| Layer | Files | What it handles |
|---|---|---|
| **MTProto transport** | `SessionConnection.cpp` | bad_msg_notification codes 16-64, bad_server_salt, ping/read timeouts, -404 auth key |
| **Session RPC** | `Session.cpp` | RPC error codes 401, 400 (connection init), auth key lifecycle on disconnect |
| **Net query dispatch** | `NetQueryDispatcher.cpp`, `NetQueryDelayer.cpp` | 303 migrate, 420 flood, 500 retry, transport-level codes |
| **Telegram business** | `UpdatesManager`, `Td.cpp`, per-feature managers | Updates gap recovery, STATE_MIGRATE from getDifference, config refresh |

The key insight: TDLib never crashes. Every error either retries (with backoff), redirects (to the
correct DC), or degrades gracefully (drops auth key, re-authenticates). The caller is notified
only when a genuine terminal condition is reached (ban, permanent revocation, or total timeout).

## Error Code -> Action Matrix

### RPC-Level Errors (from `rpc_error` in `on_message_result_error`)

| Code | Error Message Pattern | TDLib Action | Teleframe Equivalent |
|------|----------------------|--------------|---------------------|
| **400** | `CONNECTION_NOT_INITED` | Reset connection init state, change to 500, resend | Not handled (caller gets RuntimeException) |
| **400** | `CONNECTION_LAYER_INVALID` | Same as above | Not handled |
| **400** | `MSG_WAIT_FAILED` | Normalized to 400 (NetQuery::set_error) | Not handled |
| **400** | Other `400` errors | Passed through to caller; no retry | `RpcErrorException` thrown, connection stays |
| **401** | `SESSION_PASSWORD_NEEDED` | Passed through (not intercepted) | `SessionPasswordNeededException` thrown |
| **401** | `AUTH_KEY_PERM_EMPTY` (PFS) | Drop temp auth key, retry as 500 | Not handled (would hit `AuthKeyException`) |
| **401** | `AUTH_KEY_UNREGISTERED` etc. | Non-main DC or CDN: drop main key, retry as 500. Main DC: **log out** the user | `AuthKeyException` thrown |
| **420** | `FLOOD_WAIT_X` | Sleep X seconds (clamped 1..14 days), then resend | `FloodWaitException` thrown; caller sleeps |
| **420** | `FLOOD_PREMIUM_WAIT_X` | Same as FLOOD_WAIT, but also notifies speed limit state | Not handled (same as FLOOD_WAIT) |
| **420** | `SLOWMODE_WAIT_X` | Sleep X, resend | Not handled as typed exception |
| **420** | `STORY_SEND_FLOOD_*` | **Not** sent to delayer; passed through | N/A |
| **420** | `FROZEN_METHOD_INVALID` | Upgraded to 406, passed through | N/A |
| **429** | `Too Many Requests` | Generated by TDLib itself when total_timeout exceeded | N/A (TDLib generates, Telegram sends) |
| **403** | `RECAPTCHA_CHECK_*` | Sent to NetQueryVerifier (mobile only) | N/A (mobile-only) |
| **500** | `WORKER_BUSY_TOO_LONG_RETRY` | Sleep 1 second, resend | Not handled |
| **500** | Other `500` errors | Exponential backoff (doubles, capped at 60s), resend | Not handled (would be RuntimeException) |
| **503** | Transport -503 (server busy) | If `need_resend_on_503_` is false: fail with 502; otherwise backoff | Not handled |
| **< 0** | Transport-level codes | Exponential backoff (same as 500) | `RpcExceptionResolver::fromTransportCode()` only handles -404 |

### MTProto Protocol Errors (bad_msg_notification in `SessionConnection`)

| Code | Name | TDLib Action | Teleframe Status |
|------|------|-------------|-----------------|
| **16** | MsgIdTooLow | Resend message (timestamp auto-corrects) | Not handled at Client level |
| **17** | MsgIdTooHigh | **Close session** — server time difference reset + all queries resubmitted | Not handled |
| **18** | MsgIdMod4 | **Fatal** — session destroyed | Not handled |
| **19** | MsgIdCollision | **Fatal** — session destroyed | Not handled |
| **20** | MsgIdTooOld | Resend message | Not handled |
| **32-35** | SeqNo errors | **Fatal** — session destroyed | Not handled |
| **48** | bad_server_salt | Update salt from server, resend message | Not handled |
| **64** | InvalidContainer | **Fatal** — session destroyed | Not handled |

### Transport-Level Disconnects (in `Session::on_closed`)

| Condition | TDLib Action |
|-----------|-------------|
| **-404** (auth key unknown) + PFS | Drop temp key, yield to reconnect |
| **-404** + CDN | Drop main key, session failed |
| **-404** + main DC + `need_check_main_key_` | Enable PFS first; on second failure: drop main key + **log out** |
| **-404** + destroy_auth_key in progress | Drop main key (expected) |
| **500** disconnect | Resend unacknowledged queries as 500 errors (retried by delayer) |
| **Clean close** | Mark unacked queries as unknown, resend |

### Ping/Read Timeouts (in `SessionConnection::do_flush`)

| Timeout Type | Calculation | Action |
|-------------|-------------|--------|
| **Ping timeout** | Online: `RTT * 2.5`, Offline: `135 + random(0..5s)` | Close connection, trigger reconnect |
| **Read timeout** | Online: `RTT * 3.5`, Offline: `135 + random(0..5s)` | Close connection, trigger reconnect |

## Flood Wait Handling

### TDLib's Flood Wait Pipeline

```
rpc_error(420, "FLOOD_WAIT_X")
  -> Session::on_message_result_error()
    -> NetQuery::set_error(420, "FLOOD_WAIT_X")
      -> NetQueryDispatcher::dispatch() [sees error on already-sent query]
        -> code == 420 && !begins_with("STORY_SEND_FLOOD_") && !begins_with("PREMIUM_SUB_ACTIVE_")
          -> NetQueryDelayer::delay()
            -> Parse "FLOOD_WAIT_X" prefix
            -> timeout = clamp(X, 1, 14 days)   [1_209_600 seconds max]
            -> next_timeout_ = 1  (reset on explicit flood)
            -> total_timeout_ += timeout
            -> if total_timeout_ > total_timeout_limit_ (60s user / 8s bot):
                fail with 429 "Too Many Requests: retry after N"
            -> else:
                delay for `timeout` seconds, then resend
```

Key parameters:

- `next_timeout_`: starts at 1, doubles each retry when no explicit flood wait, capped at 60
- `total_timeout_`: cumulative time spent retrying
- `total_timeout_limit_`: 60s (user accounts), 8s (bots), 24h (DcAuth, ConfigManager, RSA key fetch)
- After timeout, the query is `resend()`ed (reset to Query state) and dispatched again

### Teleframe's Flood Wait Handling

```php
// AccountWorker.php - supervised poll loop
catch (Throwable $e) {
    if ($e instanceof FloodWaitException) {
        $this->interruptibleSleep(UpdatePollerService::secondsToWait($e), $shouldStop);
        continue;  // retry the poll
    }
}

// UpdatePollerService.php
public static function secondsToWait(Throwable $e): int {
    // FloodWaitException: clamp($e->seconds, 2, 3600)
    // Bot API 429: parse "retry after N", clamp same
    // Other: flat 2s
}

// Daemon.php supervisor
const BACKOFF_LADDER = [2, 5, 15, 60]; // consecutive failure isolation
```

### Differences

| Aspect | TDLib | Teleframe |
|--------|-------|-----------|
| Max single wait | 14 days (1_209_600s) | 1 hour (3600s) |
| Cumulative timeout | 60s (user) / 8s (bot) | No cumulative limit |
| Exponential backoff | Yes (1, 2, 4, ... 60) | No (flat retry after sleep) |
| FLOOD_PREMIUM_WAIT | Handled, notifies speed limit | Not distinguished |
| Interruptible sleep | Actor-based (async) | 1-second chunked sleep |

## DC Migration Protocol

### TDLib's Migration Flow

TDLib handles four migration error types, all 303-class:

```
1. FILE_MIGRATE_X (most common during file ops)
   -> NetQueryDispatcher::try_fix_migrate()
   -> net_query->resend(DcId::internal(X))
   -> Query is routed to the target DC's download/upload session pool
   -> No auth key export needed (CDN-style, server handles auth)

2. PHONE_MIGRATE_X (account belongs to DC X)
   -> set_main_dc_id(X)  // updates internal routing + persists to binlog
   -> resend query to new main DC
   -> DcAuthManager::add_dc() provisions auth key for new DC
   -> auth.exportAuthorization / auth.importAuthorization cross-DC key transfer

3. NETWORK_MIGRATE_X (network infra moved)
   -> Same as PHONE_MIGRATE (updates main DC + resends)

4. USER_MIGRATE_X (user assigned to DC X)
   -> Same as PHONE_MIGRATE (updates main DC + resends)
```

### Teleframe's Migration Handling

```php
// DcMigrationException.php
class DcMigrationException extends TelegramException {
    public int $dcId;  // target DC
    public ?string $token;  // export authorization token (for cross-DC auth)
}

// RpcExceptionResolver.php
foreach (['FILE_MIGRATE_', 'PHONE_MIGRATE_', 'NETWORK_MIGRATE_', 'USER_MIGRATE_'] as $pfx) {
    // Parse DC ID, throw DcMigrationException($dc, ...)
}

// AccountWorker.php
catch (Throwable $e) {
    if ($e instanceof DcMigrationException) {
        $dc = $e->getDcId();  // rebuild scope at the new DC
        continue;  // resume the poll loop
    }
}
```

### Differences

| Aspect | TDLib | Teleframe |
|--------|-------|-----------|
| FILE_MIGRATE | Resend to target DC (file-level) | Same DC, just exception thrown |
| PHONE/USER/NETWORK_MIGRATE | Update main DC globally + cross-DC auth export/import | Rebuild scope with new DC ID |
| Cross-DC auth | Automatic export + import | Not implemented (scope rebuild only) |
| Auth key provisioning | DcAuthManager pre-provisions keys for all 5 DCs | Session is rebuilt from scratch |
| DC options from server | Uses `DcOption` from help.getConfig | Hardcoded DC_IPS in Client.php |

## Exponential Backoff Strategy

### TDLib's Backoff (NetQueryDelayer)

```cpp
// NetQueryDelayer::delay()

// Step 1: Determine timeout
if (code < 0) {
    timeout = 0;  // use next_timeout_ (exponential)
} else if (code == 500 && message == "WORKER_BUSY_TOO_LONG_RETRY") {
    timeout = 1;
} else if (code == 420 && begins_with(message, "FLOOD_WAIT_")) {
    timeout = parse_and_clamp(message, 1, 14 * 24 * 60 * 60);
    // Also: FLOOD_PREMIUM_WAIT, SLOWMODE_WAIT, 2FA_CONFIRM_WAIT, TAKEOUT_INIT_DELAY
}

// Step 2: Exponential backoff (when no explicit timeout)
if (timeout == 0) {
    timeout = next_timeout_;        // starts at 1
    if (timeout < 60) {
        next_timeout_ *= 2;         // doubles: 1, 2, 4, 8, 16, 32, 60
    }
} else {
    next_timeout_ = 1;             // reset on explicit flood
}

// Step 3: Accumulate
total_timeout_ += timeout;
last_timeout_ = timeout;

// Step 4: Check budget
if (total_timeout_ > total_timeout_limit_) {
    // Give up: fail with 429 "Too Many Requests: retry after N"
}

// Step 5: Sleep and resend
container_[id].timeout_.set_timeout_in(timeout);
// After timeout: query->resend(), re-dispatch
```

**Backoff sequence for unknown 500 errors:**
1s -> 2s -> 4s -> 8s -> 16s -> 32s -> 60s -> 60s -> ... -> total exceeds 60s -> fail

**After explicit FLOOD_WAIT_X:**
X seconds (once) -> next_timeout_ reset to 1 -> if failure continues: 1s -> 2s -> ...

### Teleframe's Backoff

```
Daemon supervisor:
  [2, 5, 15, 60] seconds isolation ladder (consecutive failures)
  healthy tick resets failure count

UpdatePollerService:
  FloodWait: clamp($seconds, 2, 3600) -> sleep -> retry
  Unknown error: flat 2s -> retry
  No exponential backoff
  No cumulative timeout

AccountWorker:
  3 consecutive unexpected failures -> rethrow to supervisor
  DC migration: instant retry at new DC
```

### Recommendations

| Gap | Severity | Recommendation |
|-----|----------|----------------|
| No exponential backoff for 500/transport errors | High | Add doubling backoff [1, 2, 4, 8, 16, 30] capped at 30s in AccountWorker |
| No cumulative timeout for unknown errors | Medium | Add total_timeout tracking; after N minutes of consecutive failures without progress, escalate to supervisor |
| FLOOD_PREMIUM_WAIT not distinguished | Low | Handle FLOOD_PREMIUM_WAIT_X the same as FLOOD_WAIT_X (Teleframe already sleeps X seconds) |
| MAX_BACKOFF 3600s too high | Medium | Consider 600s (10 min) max for individual flood waits; if it exceeds that, let the supervisor isolate the account |
| No server-reported DC options | Medium | Call `help.getConfig` to obtain real DC IP/ports instead of hardcoded `DC_IPS` |
| No cross-DC auth export/import | Low | Not needed for single-DC use; implement only if multi-DC routing is added |

## Connection State Machine

### TDLib's StateManager

TDLib's `StateManager` (extends `mtproto::ConnectionManager`) exposes a four-state machine
to the application via callbacks:

```
WaitingForNetwork  (network_flag_ == false)
       |
       v
Connecting  (network is up, but connect_cnt_ == 0)
       |
       v
  Updating  (connected, but sync_flag_ == false)
       |
       v
   Ready   (connected and synchronized)
```

**Debounce constants:**
- `UP_DELAY = 0.05s` (state improving transitions are fast)
- `DOWN_DELAY = 0.3s` (state degrading transitions are delayed to avoid flicker)

**Connection count tracking:**
- `inc_connect()` / `dec_connect()` called by `ConnectionToken` RAII guard
- `connect_cnt_` tracks active encrypted connections
- `connect_proxy_cnt_` tracks active proxy connections
- State is `Connecting` when `connect_cnt_ == 0` (any one connection brings us to Updating)

**State transitions triggered by:**
- Network change (`on_network()`)
- Connection established/closed (`ConnectionToken`)
- Synchronization complete (`on_synchronized()`)
- Online/offline toggle (`on_online()`)
- Proxy state change (`on_proxy()`)

### Teleframe's Connection State

Teleframe has **no equivalent state machine**. The `Client.php` operates a single cached
`EncryptedConnection` with lazy connection:

```php
protected function ensureConnection(): EncryptedConnection {
    if ($this->conn !== null) {
        return $this->conn;
    }
    // ... handshake + encrypted connection
}

public function call(string $method, array $params = []): array {
    try {
        $conn = $this->ensureConnection();
        return $conn->call($method, $params);
    } catch (TelegramException $e) {
        throw $e;      // RPC: connection stays
    } catch (RuntimeException $e) {
        $this->close(); // Transport: evict connection
        throw $e;       // Caller must handle retry
    }
}
```

### Recommendations

- **Production polling** (Daemon/AccountWorker) already manages reconnection implicitly
  through the catch-and-retry loop
- **State machine not needed** at the Client level for Teleframe's architecture
  (the Daemon supervisor provides equivalent reliability)
- A `ConnectionState` enum could be useful for **observability** (logging/health checks)
  without the full StateManager complexity

## State Resync After Disconnect

### TDLib's Resync Protocol

When TDLib reconnects (new `new_session_created` or after disconnect):

1. **All unacknowledged queries are resent** — `Session::on_closed()` iterates `sent_queries_`
   and resubmits unacked ones
2. **Updates gap detection**: TDLib compares `first_msg_id` from `new_session_created` against
   stored update state; any messages before `first_msg_id` are considered lost
3. **getDifference is forced**: on `new_session_created`, TDLib sends `updatesTooLong` to force
   an immediate `updates.getDifference` call (in `Session::on_new_session_created`)
4. **Auth key lifecycle**: On -404 (auth key unknown), TDLib has a cascading fallback:
   - Try PFS (temp key) first
   - Then try without PFS
   - Then check main key validity
   - Finally, log out (main DC, main key)

### Teleframe's Resync Protocol

Teleframe implements the `updates.getDifference` state machine in `UpdatePollerService`:

```
updates.difference       -> adopt full state, gap resolved
updates.differenceSlice  -> adopt intermediate_state, keep fetching (immediate retry)
updates.differenceTooLong -> hard-reset pts to server value, flag gap
updates.differenceEmpty  -> adopt state, gap resolved
```

**After disconnect** (in AccountWorker):
1. DcMigrationException -> rebuild scope at new DC, resume difference window
2. FloodWaitException -> sleep, then retry poll
3. Unexpected error (3 consecutive without progress) -> rethrow to Daemon supervisor
4. Sequence state (pts/date/qts/seq) survives across restarts via `$resumeState`

### Gaps/Improvements

| Aspect | TDLib | Teleframe |
|--------|-------|-----------|
| Unacked query resend | Automatic on disconnect | Not applicable (stateless call()) |
| New session forces getDifference | Yes | No (relies on poll loop naturally retrying) |
| pts/date/qts persistence | Stored in TDLib's binlog | Passed as constructor arg (host must persist) |
| Channel pts tracking | Per-channel pts map | Implemented (`$channelPts` in UpdatePollerService) |
| Gap events | Internal only | TelegramGapDetected + TelegramResynced events |

## Comparison with Teleframe

### What Teleframe Does Well

1. **Typed exception hierarchy**: `FloodWaitException`, `DcMigrationException`, `AuthKeyException`
   are well-designed and carry actionable data (seconds, dcId, etc.)
2. **Supervisor architecture**: The Daemon's backoff ladder [2, 5, 15, 60] with all-fail
   give-up is sound and production-ready
3. **Interruptible sleep**: Both AccountWorker and UpdatePollerService chunk sleep into
   1-2 second pieces, making shutdown responsive
4. **Sequence state survival**: The resumeState pattern ensures the difference window
   is never lost across daemon restarts
5. **Zero-regex error parsing**: `RpcExceptionResolver` uses `sscanf` and `strspn` instead
   of regex, matching TDLib's C++ style and Teleframe's zero-regex constraint
6. **Connection eviction on transport failure**: `Client::call()` evicts the cached
   connection on RuntimeException, preventing stale connection reuse

### What Teleframe Is Missing

1. **No exponential backoff for transport/500 errors** — flat 2s sleep is wasteful for
   transient server errors
2. **No cumulative timeout tracking** — unknown errors can retry indefinitely in
   AccountWorker (only the 3-strike consecutive-without-progress limit applies)
3. **No FLOOD_PREMIUM_WAIT distinction** — no speed limit notification to the application
4. **Hardcoded DC IPs** — should call `help.getConfig` to get server-provided DC options
5. **No connection state observation** — no way for the host application to know if the
   engine is Connecting/Updating/Ready
6. **No automatic cross-DC auth export** — DcMigrationException carries a `$token` field
   but the auth.exportAuthorization/auth.importAuthorization flow is not implemented

## Recommendations

### Priority 1: Exponential Backoff in AccountWorker

Add a doubling backoff for non-flood transport errors:

```php
// In AccountWorker::run()
$transportBackoff = 1;
// ...
catch (Throwable $e) {
    // ... existing FloodWait and DcMigration handling ...

    // Transport / 500 error: exponential backoff
    $this->interruptibleSleep(
        min($transportBackoff, 30),  // cap at 30s
        $shouldStop
    );
    $transportBackoff = min($transportBackoff * 2, 30);

    if (++$unexpected >= self::MAX_UNEXPECTED_FAILURES) {
        throw $e;
    }
}

// Reset on progress
if (self::progressed($state, $fresh)) {
    $unexpected = 0;
    $transportBackoff = 1;
}
```

### Priority 2: Cumulative Timeout for Unknown Errors

Track cumulative retry time; after 5 minutes of non-flood, non-migration failures, escalate
to the supervisor:

```php
$totalRetryTime = 0;
// ...
catch (Throwable $e) {
    // ... flood/migration handling ...
    $totalRetryTime += $transportBackoff;
    if ($totalRetryTime > 300) {
        throw $e; // let Daemon isolate the account
    }
}
// Reset on progress
if (self::progressed($state, $fresh)) {
    $totalRetryTime = 0;
}
```

### Priority 3: Dynamic DC Resolution

Replace hardcoded `DC_IPS` with a `help.getConfig` call at session init:

```php
// In TeleframeClient or UserAccountScope
$config = $scope->call('help.getConfig', ['hash' => 0]);
foreach ($config['dc_options'] ?? [] as $opt) {
    // Store DC IP/port mapping
}
```

This is lower priority because Telegram rarely changes DC IPs, but it improves
resilience for long-running processes.

### Priority 4: Connection State Observation

Add a lightweight `ConnectionState` enum for health check integration:

```php
enum ConnectionState { case Connecting; case Ready; case WaitingForNetwork; }
```

Exposed via a `getState()` method on the Client or a callback hook. This is observability-only
and does not change behavior.
